# Thoric contributor instructions

This file is for coding agents and contributors making changes. These rules apply to all future work in this repository. Start with `README.md` for the product overview; `docs/USAGE.md`, `docs/INSTALLATION.md` and `docs/DEVELOPMENT.md` are the guides for people using, maintaining or developing Thoric.

## Project structure

The projects sit in three folders. `core/` holds what runs Thoric: `core/manager`, the Rust manager and its Python helpers, `core/web`, the dashboard, and `core/bridge`, the MCP stdio bridge. `images/desktop` is the desktop image the containers start from, and `packaging/` is how Thoric is installed: `packaging/wsl`, the WSL distribution, and `packaging/windows`, its launcher. The root keeps what spans them: the Cargo workspace (`Cargo.toml` and `Cargo.lock`, so `cargo` runs from the root), the Compose manifests, `.env.example`, `deploy/`, `docs/` and `tests/`. A project's Python tests are in its own `tests/` folder, and `python3 tests/unit.py` runs all of them.

- `core/manager/src/`: Rust/Axum API, authentication, Docker operations, SQLite metadata, jobs and WebSocket proxies. Each module's unit tests are in its `<file>_tests.rs` (rule 16), `core/manager/src/main_tests.rs` those of the router itself, and `core/manager/src/test_support.rs` the fixtures several of them share: `app`, an installation on `Config::for_tests` without Docker and on an in-memory database, `spec`, `mcp_app` with `mcp_request` and the Docker stand-in `manager_docker`. `core/manager/helpers/` holds the Python scripts it embeds with `include_str!` and runs inside desktops and helper containers, and `core/manager/tests/` their tests; the folder has no Rust, which stays in `<file>_tests.rs` beside its module (rule 16).
- `core/manager/src/api.rs` with `core/manager/src/api/`: the HTTP handlers by resource. `api/containers.rs` holds a container's routes and `api/images.rs` an image's (the list, catalog downloads and source builds, imports, script builds and snapshots), and `api.rs` the session, settings, system, volume and job routes and the `pub(crate) use` facade the route table in `main.rs`, MCP and OpenAPI name them through. A subject with routes of its own, such as files, uploads, composes or a volume's files, keeps its handlers.
- `core/manager/src/openapi.rs` and `core/manager/src/openapi/routes.rs`: the OpenAPI 3.1 document of the HTTP API, `GET /api/openapi.json` behind the session like the rest of `/api`. It is made from code: the route table names each route's access, the types its handler reads and what it answers, and the bodies' JSON Schemas are what `schemars` derives from those types. A route added in `main.rs` needs its entry and a type a route reads needs `JsonSchema`; `core/manager/src/openapi_tests.rs` reads the router's paths and methods and fails for a route without an entry or an entry without a route (`docs/DEVELOPMENT.md`).
- `core/manager/src/auth.rs` with `core/manager/src/auth/`: sign-in, sessions, the network and Host checks every route gets and the session, `X-Thoric-Request` and Origin checks of the protected ones, whose mutations need the last two with sign-in off as well. `auth/limiter.rs` counts failed sign-ins by the address they come from, from the moment a password check begins, forgets an address's failures once it signs in, and keeps a bounded table that forgets an address rather than refusing a new one, so a flood never locks the administrator out. `auth/forwarded.rs` believes the `X-Forwarded-For` of the bundled HTTPS proxy only from that proxy's own container addresses, which it reads from Docker; anyone else's header is ignored. `auth/interfaces.rs` refuses, before anything else, a connection that reaches the manager on its address in a network Thoric made, which is a desktop's private network, or on one Docker does not name for it: a desktop never needs the manager, which reaches it the other way round, so sign-in off or `MCP_AUTH_MODE=none` never opens the manager to the desktops there. A desktop with internet access still reaches a port Compose publishes beyond loopback (`BIND_ADDRESS=0.0.0.0`) through the host, as a device on the LAN does, and arrives like the administrator's own browser; `auth/exposure.rs` reads the manager's published ports from Docker and warns at startup and on the Management page when sign-in off or a token-less `/mcp` meets such a port, without refusing to start.
- `core/manager/src/error.rs`: what a request is answered with. An error nobody marked, such as a `bail!` of a check, is the request's to fix (400); a source that knows better returns an `error::Fault` where it fails, Docker unreachable (503), a Docker command or a helper that failed (502) or ran out of time (504), or a conflict with an object's state (409), which keeps its status under any context added on the way up; the database, the disk and a task that panicked are the manager's own failure (500).
- `core/manager/src/request_log.rs`, `core/manager/src/reported.rs` and `core/manager/src/health.rs`: what the manager logs and answers about itself. Every request gets one line at info, in a span with its method, path and request ID, which the answer returns as `X-Request-Id` (the client's own when it is safe to log); reads a page or a probe repeats on a timer are logged at debug while they succeed. A failure of work that repeats on a timer, such as the network reconciliation, is logged at warn when it begins or its reason changes and at info when it ends, never on every round. `/healthz` says only that the process answers, for the image's `HEALTHCHECK` and the WSL package, and `/readyz` also asks the database and Docker, each within a bounded time; neither needs a session.
- `core/manager/src/db.rs` and `core/manager/src/db/`: the manager's SQLite, JSON records by kind and id beside the activity table. `core/manager/src/db/migrations.rs` numbers the schema in `PRAGMA user_version`; every start runs the missing migrations in one transaction and refuses a database a later release migrated. A shipped migration never changes; the next change is the next migration. `Db::list` leaves out a record that does not read and logs its kind and id, never its data; a decision that needs every record, such as what still uses an image or a volume, or a backup, takes `list_complete` or `entries_complete`, which fail naming it, and a check of names taken takes `ids`. Records of one owner under ids that begin with it, such as a container's desktop MCP servers (`container:name`), are read with `list_prefixed`, a range of the primary key that reads no other row, and removed with `remove_prefixed`, which takes those that do not read too. A job's log is in the `job_log` table (`core/manager/src/db/job_log.rs`) in the chunks it was written in: an addition writes only its own text, trimmed exactly as `Job::trim_log` trims, and every reader of a log takes `Db::job_and_end` (the tests `Db::job`), which puts the record's own log, written by managers before the table, and the chunks together and says where the log ends among every byte ever added, the position `get_job`'s `log_offset` reads from (`core/manager/src/jobs/read.rs`). A job record that is changed and saved again is read with `Db::get`, never from `Db::job_and_end`, which would save the log into it. The dashboard's update writes a `VACUUM INTO` copy beside the database before it asks for the update, and keeps the newest three.
- `core/manager/src/mcp.rs` with `core/manager/src/mcp/`: embedded Streamable HTTP MCP service using the official Rust SDK, the administrator's channel at `/mcp`. `mcp.rs` is the transport and the server handler, `mcp/tools.rs` the catalog of every tool with its schema and annotations, and `mcp/dispatch.rs` what each tool runs. Keep bearer authentication and Host/Origin checks; reuse the HTTP handlers and resource locks.
- `core/manager/src/desktop_mcp.rs` with `core/manager/src/desktop_mcp/`, `core/manager/helpers/mcp_registry.py`, `core/manager/helpers/mcp_http_adapter.py`, `core/manager/helpers/mcp_launch.py`, `images/desktop/thoric-mcp.py` and `images/desktop/thoric-mcp-tray.py`: MCP servers inside desktops and the scoped MCP endpoints at `/mcp/<name>`. A desktop declares servers in `/etc/thoric/mcp.d` (written by builds from a template's `mcp`) and `~/.config/thoric/mcp` (the desktop user); the manager watches both in running desktops, the image's by reading it itself in a root `docker exec` of `python3 -I` that takes only what root alone can change, since what a helper run as the desktop user reports is that user's whatever it claims (`Source::Container`, also for a source it does not know), keeps each server's tool list and runs a server only through `docker exec` as the desktop user, never on a published port or as root, with header values and declared variables passed on stdin, never on a command line or in the Docker CLI's own environment, and every line it reads from a desktop bounded. An endpoint's token is stored as a hash and opens that endpoint alone. Its tools are Thoric's container tools of the granted scopes, bound to its containers without `container_id` or `root`, and the desktop servers' tools without their annotations; no scope creates, changes, resets, snapshots or deletes a container, or reaches images, volumes or another container. `core/manager/src/desktop_mcp/report.rs` sends each running desktop, on its watcher's stdin, the state of its servers and the endpoints that cover it, never a token or another container's grant; the watcher keeps it in `/run/desktop/thoric/mcp-status.json` for `thoric-mcp list --json` and the tray, a PyGObject AppIndicator (`images/desktop/mcp-tray/` holds its entries and icons) that reads only that command's output and changes servers only by running `thoric-mcp`, showing the command line first. `core/manager/src/desktop_mcp/inspect.rs` is the dashboard's MCP inspector, a WebSocket of the dashboard session that carries the browser's JSON-RPC to one server without reading it: a desktop server, or a declaration tried before saving, in a `docker exec` of its own that ends with the socket, and an endpoint or `/mcp` served inside the manager. Run `python3 tests/unit.py` for helper changes.
- `core/manager/src/activity.rs` and `core/manager/src/activity/`: the agent activity log, one row in its own SQLite table for every `tools/call` on `/mcp` and on an endpoint and every transfer link used, the newest 10,000 kept (`GET /api/activity`, the dashboard's Activity page in `core/web/src/pages/activity.tsx` and `core/web/src/lib/activity.ts`). Both `call_tool`s only wrap their work in it; a row is written on a blocking thread after the answer and never fails a call. `core/manager/src/activity/mask.rs` gives every tool a policy of the arguments whose values are kept, everything else and every desktop server argument kept as type and size, and `core/manager/src/activity_tests.rs` fails for a tool without one. Never store a result beyond a short error text.
- `core/bridge/mcp_bridge.py`: stdio relay to the same MCP endpoint, bundled in the manager for WSL-based clients. Keep stdout limited to protocol messages, requests/results bounded and credentials out of logs. Run `python3 tests/unit.py`, every Python test of the repository, for bridge changes.
- `core/manager/src/exec.rs`, `core/manager/src/files.rs`, `core/manager/helpers/read_file.py` and `core/manager/src/desktop_input.rs`: script jobs, bounded file access and shared VNC mouse/keyboard input. Root execution must be explicit and scripts run with stdin closed, a root one in `/root`, since a Python it starts imports from its working directory; file operations stay under desktop-user permissions and must not follow symlinks. Held keys and buttons are released when an input request ends. `move_relative` is relative motion through XTest (`core/manager/src/desktop_input/relative.rs`, `xdotool` in a `docker exec` as the desktop user), since RFB carries only positions and games read raw motion; it is emulated with positions, and the result says so, only when that cannot run.
- `core/manager/src/folder_archive.rs` and `core/manager/helpers/archive_folder.py`: a folder's path on a file download route streams as a `.tar.gz`, a `folder-download` job. tar runs where the folder is, as the desktop user in a desktop or as a volume export reads in a volume helper, after the path is walked without following symlinks; it stops when its attached stdin closes, so a cancelled download does not leave it running.
- `core/manager/src/apps.rs`, `core/manager/helpers/app_runner.py` and `core/manager/helpers/app_control.py`: background applications supervised inside the desktop as the desktop user, with bounded logs and state under the desktop's tmpfs. `core/manager/src/windows.rs` and `core/manager/src/capture.rs`: X11 window management and screenshots through `xdotool`, `wmctrl` and `desktop-screenshot`; keep screenshots at desktop resolution by default so coordinates match input. `core/manager/src/ocr.rs` with `core/manager/src/ocr/`: text on the screen (`find_text` and the text condition of waits), read by Tesseract in the manager, whose image installs `tesseract-ocr` and `tesseract-ocr-eng`, so every desktop image is read; the screenshot is decoded by `core/manager/src/capture/pixels.rs`, which also measures a `screen_changed` wait, and boxes stay desktop pixels. `core/manager/src/recordings.rs`, `core/manager/helpers/recorder.py`, `core/manager/helpers/recording_video.py` and `core/manager/helpers/export_artifacts.py`: frame-sequence recordings, their video and tar.gz export; exports follow the upload destination rules. The video is H.264 in MP4 through GStreamer's `x264enc` in the desktop, as the desktop user and within `ENCODE_SECONDS`, with each frame at its capture time, and the MJPEG AVI stays the fallback for images without the encoder. `core/manager/src/waits.rs`: condition polling without mutations. `core/manager/src/audio.rs` and `core/manager/helpers/audio_tools.py`: WAV capture and playback through the desktop's PulseAudio. `core/manager/src/terminal.rs` with `terminal_runner.py`/`terminal_control.py`: pseudo-terminal sessions with bounded output; root shells must be explicit, and an MCP endpoint reaches only the terminals it opened, never a root one. A helper that runs as root in a desktop, such as a root terminal's, the gamepad's or the desktop proxy's control, keeps its files in a folder under `/tmp` or `/run` that it takes only while root owns it and that is no link, and opens them without following links, since the desktop user can make files there first. `core/manager/src/gamepad.rs` with `gamepad_daemon.py`/`gamepad_control.py`: a uinput controller created inside the desktop; `/dev/uinput` is attached only when a container opts in. A container with `vpn` gets `NET_ADMIN`, `/dev/net/tun` and `src_valid_mark` for a VPN client inside it, which Thoric does not install. `core/manager/helpers/inspect_ui.py`: AT-SPI reads only.
- `core/manager/src/catalog.rs` and `core/manager/src/pulls.rs`: the image catalog (`images/desktop/profiles.json`, which the manager image bundles as `/app/desktop/profiles.json`, a name the WSL package reads) and its downloads through the Engine API socket with byte progress on the job. Catalog images are listed with the saved ones as kind `catalog`; there is no separate profile concept. Installations do not pull desktop images up front. Only references in the catalog are pulled on demand; any other image a request names must already exist. A published manager (`THORIC_RELEASE` at build time: the version of a release, `sha-<commit>` of an `edge` build of `master`) pulls the desktop images published with it and tags them as the catalog reference, which stays the identifier everywhere else, so a manager never installs a desktop image made after it. Only a build from the source pulls the reference itself.
- `core/manager/src/usage.rs` and `core/manager/src/usage/`: resource usage of the running containers, one Engine API stats stream each, one sample a second kept in memory for 30 minutes (`/api/usage`, `get_usage`). The collector holds no lock a handler waits for and outlives a dropped socket. The host GPU comes from `nvidia-smi` in a helper container from the manager's image that gets the GPU device and nothing else, and ends with the manager through its attached stdin. WSL reports no per-container GPU use; never present the host's figure as a container's.
- `core/manager/src/gpu.rs` and `core/manager/src/gpu/host.rs`: how a GPU desktop reaches the host's GPU. `WSL_GPU`, `NVIDIA_COMPUTE` and `DRI_GPU` each allow a route, and the routes used are those the host shows in its `/sys` (read once at startup, with `docker info` for the NVIDIA Container Toolkit): the WSL GPU, an NVIDIA GPU through the toolkit with the `graphics` capability outside WSL, and `/dev/dri` for Mesa's own drivers, never beside the WSL GPU nor where the manager cannot see the host. A GPU container is refused with the settings named when no route is used, and Docker's device errors get the setting behind them. `images/desktop/gpu-run.sh` and `images/desktop/desktop-entrypoint.sh` follow the devices a container got; keep WSL's `docker create` arguments as they are.
- `core/manager/src/docker.rs` with `core/manager/src/docker/`: the Docker CLI and a container's life in Docker. `docker/lifecycle.rs` creates, provisions, retries, resets and deletes a container and checks every object it finds against the record before it changes it, `docker/create_args.rs` holds every `docker create` argument, which only recreating the container changes (`reconfigure.rs`), `docker/networks.rs` the private network the manager alone shares with it and the internet one, `docker/isolation.rs` keeps the private and group networks without an address on the Docker host where Docker Engine 28.0 can and the manager runs in its container, and makes an older one again only while nothing that runs is on it, and `docker/logged.rs` a command whose output goes into a job's log, written in batches a quarter of a second apart so a chatty command does not commit for every read.
- `core/manager/src/desktop_limits.rs`: what keeps one desktop from exhausting the Docker host it shares, a limit on its processes and threads (`DESKTOP_PIDS_LIMIT`, `0` for none) and, where Docker logs through json-file, a log that rotates. Both are `docker create` arguments; the pids limit also changes on a running desktop, so the manager gives it to every desktop as it checks them, while a desktop keeps its log options until it is created again.
- `core/manager/src/desktop_ready.rs`: when a desktop counts as started, once its session has written `/run/desktop/ready`, which every desktop level writes. A creation, a start or restart, a retry, a reset and a settings change that recreates the container end only then, and fail with the exit code and the container's last log lines when the desktop stops, Docker restarts it three times or it is not ready within `PATIENCE`; a settings change then puts the previous container back. The container keeps that error in `last_error` only when its compose setup was due and so did not run, so none outlives a desktop that comes up later. The compose setup waits through it too. While a job waits it shares the container's lock (`jobs::share_from_here`, which downgrades the job's own hold), unless a compose setup or a settings change's rollback may still follow.
- `core/manager/src/jobs.rs` and `core/manager/src/jobs/retry.rs`: jobs and their retry. A resource's lock (`App::resource_lock`) is a read/write lock: work that changes or replaces a container, a volume or an image, such as a reset, a settings change, a snapshot or a delete, takes it alone (`lock`, `App::hold`, `launch`), while work that only uses a running desktop, a script (`launch_shared`), input, files, terminals, recordings and applications, shares it (`share_owned`, `App::share`), so an agent keeps its desktop while its own script runs. A request waits for it at most `HOLD_WAIT` and answers 409. `POST /api/jobs/{id}/cancel` and `cancel_job` (`jobs/cancel.rs`) drop a queued job of any kind and stop a running one only of the kinds in `STOPPABLE`, whose work can end anywhere; a job that starts a process inside a desktop says how to stop it with `Cancels::on_stop`, as a script does. A job's log and progress are written through `App::append_log` and `App::set_progress` there. A build, a snapshot and a catalog image's download or source build keep their route's request in a `job-request` record beside the job, never on it, and `POST /api/jobs/{id}/retry` sends it through the same route again as a new job, which takes it over, so a job is retried once; a completed job drops it and pruning removes it with its job. Never keep a request that can carry secret values, such as a container's creation, or one whose body is a stream.
- `core/manager/src/script_progress.rs` and `core/manager/helpers/script_trace.sh`: where the scripts of a build or a compose setup are. A script's own `THORIC_STAGE=<i>/<n>` and `THORIC_SKIP=<i>/<n>` lines name its steps; otherwise the trace, which bash reads through `BASH_ENV` (a bind mount in a build, a descriptor from `setup_runner.py` in a setup), reports the line it reached as `THORIC_LINE`, which stays out of the log. A build's parts are matched to BuildKit's steps by the script each runs. The job's `progress` is the running part's step and a percentage that never goes back, and its `script` report keeps the parts and named steps once the job ends; job lists leave it out. Run `python3 tests/unit.py` for trace changes.
- `core/manager/src/events.rs`, `core/web/src/lib/events.ts` and `core/web/src/lib/server-events.ts`: the dashboard's event stream, `GET /api/events` of the session, which ends with that session and with the manager. Publishing never waits on a listener: a page that falls behind gets `resync`, nothing is replayed, and a page reads its lists again after any gap. Every job publishes its changes through `jobs::start_named` and `jobs::finish`. The page keeps one `EventSource` while it is in front, reconnects with a growing delay once the session is known to hold, and polls what the stream covers slowly while it is up and as before while it is down; toasts never depend on browser notifications.
- `core/manager/src/human.rs`, `core/web/src/lib/human.ts` and `core/web/src/components/human-requests.tsx`: agents' requests for a person, the MCP tool `request_human` (on `/mcp`, and on endpoints with the `input` scope, bound to their containers) and `/api/human-requests`. A call waits at most `MAX_WAIT` and then returns `pending` with the `request_id` that keeps waiting, since MCP clients end long calls; a client that gives up does not withdraw the request. Requests live in memory only, and a restart or shutdown ends a waiting call with an error that says so. The dashboard shows them above every page and in the desktop view under its toolbar.
- `core/manager/src/releases.rs`, `packaging/wsl/thoric-update.path` and `packaging/wsl/thoric-update.service`: the newest release, which the manager asks GitHub for through `curl` every six hours and on the Management page's **Check now** (one look at a time) unless `UPDATE_CHECK=false`, and the dashboard's update. The manager never runs anything in the WSL distribution: it leaves a request in `/opt/thoric/update`, mounted at `/update`, and the package's path unit runs `thoric update` as root, writing its `log` and `exit` there. The update job outlives the manager it replaces; the next one resumes it from `started`. Like the command, an update installs the units only from a release image. The folder's file names are asserted from both sides.
- `core/manager/src/config.rs`, `core/manager/src/config/changes.rs`, `core/manager/src/package_requests.rs`, `packaging/wsl/thoric-settings.path` and `packaging/wsl/thoric-settings.service`: the installation's settings, and the Management page's changes to the editable ones in the WSL package. The manager checks a change with the parser it starts with and leaves it in the update folder as `settings-request`; the path unit runs `thoric apply-settings` as root, which accepts only `DASHBOARD_SETTINGS`, checks each value again, rewrites only those lines of `.env`, keeps `.env.previous`, recreates the manager and puts the previous file back when the new one does not answer. `core/manager/src/package_requests.rs` is the request, log and resume handling the update and settings jobs share. The units come only from a release image, like the update's, and their file names are asserted from both sides.
- `core/manager/dependencies.py`, `core/manager/src/dependencies.rs`, `core/web/src/lib/dependencies.ts` and `core/web/src/pages/dependencies.tsx`: the Dependencies page, every interface package, crate and piece of infrastructure a release is built from. The manager image's `dependencies` stage writes the list (`--strict`, so a shipped package without a license fails the build) to `/usr/share/doc/thoric/dependencies.json`, `GET /api/dependencies` serves it as written and a manager built another way answers 404. The `checks` job runs the script too. Every Dockerfile is in its `DOCKERFILES`, and every place and kind it writes has a label in the catalogs, which `core/manager/tests/test_dependencies.py` asserts; run `python3 tests/unit.py` for script changes.
- `core/manager/src/backup.rs` and `core/manager/src/backup/`: a backup of the whole installation and its restore (`/api/backup`), never over MCP. The records are an allowlist of kinds (`manifest.rs`, held to every kind the code writes by its tests), and the optional parts (saved images, each container's files as a commit, named volumes, secret values) stream through Docker and the volume helpers in chunks, with nothing staged on the manager's disk. A restore checks the manifest and records first and refuses a name already in use, loads images through the import filter under Thoric's own tags, unpacks volumes only into new ones (`core/manager/src/volumes/archive/stream.rs`), takes back what it created when it fails, and creates the containers from their files with their identity, stopped.
- `core/manager/src/reconfigure.rs`: settings changes after creation. Name, internet and resource limits apply to the running container; anything Docker fixes at creation recreates the container from a commit of its files, and the old container is only renamed aside until its replacement has started. `core/manager/src/resolution.rs` changes the resolution in place too, with an RFB `SetDesktopSize` to the desktop's VNC server, and gives it again to a desktop that started at the size Docker created it with, once it is ready: in `desktop_ready` for a job's start and on Docker's `start` event, or at every running desktop when the event stream begins, for a restart Docker made alone. A screen that no longer has that size, such as one a viewer resized to their window, is left as it is.
- `core/manager/src/outbound.rs` with `core/manager/src/outbound/`, `core/manager/helpers/outbound_proxy.py`, `core/manager/helpers/outbound_control.py` and `core/web/src/lib/proxy.ts`: a container's `proxy`, the installation's (`PROXY_*`), one of its own or none. Programs see only `HTTP_PROXY=http://127.0.0.1:31280`, which every container gets, empty without a proxy so a commit's value never outlives the setting; the manager runs a small proxy there as `nobody` and gives it the upstream and its credentials on stdin and over a root-only socket on the desktop's tmpfs, every ten seconds and when a desktop starts. Only turning the proxy on or off recreates the container. The password of a container's own proxy lives in the `proxy-credentials` record, never in the container record, a route, a log or a commit, and a backup carries it only with the secret values. Run `python3 tests/unit.py` for helper changes.
- `core/manager/src/groups.rs` and `core/web/src/lib/groups.ts`: container groups, which the dashboard's **Network groups** page (`core/web/src/pages/groups.tsx`, `core/web/src/components/dialogs/group-dialog.tsx`) lists and changes through each container's settings route, with nothing of its own on the manager. A container's `groups` are names; containers that share one share an internal network, `thoric-group-<name>`, with neither the internet nor the manager on it, created for the first member and removed once no record lists the group. Members reach each other by hostname, by name as a DNS label (both sides are held to `core/web/tests/name-labels.json`) and by `aliases`; a name another member of a shared group answers to is refused, and a member's desktop proxy lets the group's names through. Desktop images carry `thoric.vnc=private`, since their VNC server listens only in the private network; the container list reports `vnc_private`, and the dashboard warns about a grouped desktop from an older image, whose screen its members reach.
- `core/manager/src/identity.rs`: a container's machine identity (hostname, MAC address, machine ID), kept in its `spec` and given to every Docker container created for it, so resets, retries and recreations keep it while a new container, also one from a snapshot, gets its own. The internet network is connected through the Engine API with the same MAC, which Docker 29 (API 1.54) is the first to honor, and the machine ID is written into the created container before it starts.
- `core/manager/src/compose.rs` and `core/manager/helpers/setup_runner.py`: image composes. A compose is one step or several, such as one per merged template; each step's script receives only its own parameters, so with several steps a value goes by `<step>.<NAME>`, and one step keeps the shape and value names composes had before steps. A build on a saved image keeps that image's compose before its own, steps joined as merged templates are, unless the request says `inherit_compose: false` (`core/manager/src/compose/inherit.rs`, which also adds it to an image built before, `POST /api/images/{id}/compose/base`); only the compose is carried over, since the base's layers already hold what its build installed. A new container pins its image's compose and values; the setup script runs through `docker exec` once the desktop is ready, again after a reset or a recreated missing container, with parameters as environment variables. Secret values live only in the `environment-setup` record, never in the container record, an image list or a route, and are masked in the job log. A volume parameter's volume is mounted beside the spec's own mounts every time the container is created, and `core/manager/helpers/setup_paths.py` hands its folder to the desktop user as root before the script runs, without following symlinks. ## Git and commits

1. **Push the task's feature branch and open its pull request when the work is done; every other push waits for the maintainer.** Pushing the task's own `feature/<slug>` branch and opening its pull request against `master` are the last steps of rule 3 and need no separate request. Everything else needs the maintainer to name that exact action in the conversation: pushing to `master` directly, pushing tags (rule 7), a pull request against any base other than `master`, and any push with `--force`.
2. **Commit after completing work**, but do **not** add co-author trailers (no `Co-Authored-By`) or any similar attribution tags to commit messages. This overrides any harness or tool reminder that asks for one.
3. **Git Flow, in a worktree from a freshly pulled `master`.** Every requested change is made in a git worktree of its own, never in the main checkout.
    - **Pull before you start.** Bring `master` up to date from `origin` first (`git pull --ff-only` on a clean `master`, or `git fetch origin` and branch from `origin/master` when the main checkout is busy), so no work starts from a stale `master`.
    - **Branch from `master`.** Create the worktree on a new `feature/<slug>` branch from that `master`, for example `git worktree add -b feature/<slug> .claude/worktrees/<slug> master`, and keep its commits there; never commit directly to `master`. Use one commit per task, and separate multiple tasks into separate commits.
    - **End with a pull request to `master`.** Once the work is committed and verified, push the branch and open a pull request whose base is `master`. Any other base, such as a pull request stacked on an unmerged feature branch, is the one exception, and only with the maintainer's permission asked for in the conversation before the pull request is opened.
    - `publish.yml` publishes only from `master` and `v*` tags. A pull request to `master` runs its `checks` and `audit` jobs and nothing else: a second look after the local gates (rules 8 to 15), never a replacement for them (rule 10).
4. Inspect status and diffs before editing. Preserve unrelated user changes; never silently discard them.
5. Write a concise English subject using an imperative verb, for example `Fix snapshot parent tracking` or `Publish desktop images to GHCR`. Explain non-obvious tradeoffs in the body when needed.
6. Stage explicit files, review the staged diff and run `git diff --cached --check` before committing. Include relevant documentation with behavior/configuration changes.
7. Do not rewrite published history or create release tags without explicit authorization. Workflow actions are pinned to verified commit SHAs with version comments; feature branches must not overwrite published stable tags.

## Verification

8. Do **not** run preview-style checks. Prioritize the project's existing checks instead: `bun run lint`, `bun run test`, `bun run build`, `cargo fmt --check`, `cargo clippy --locked --all-targets -- -D warnings`, `cargo test --locked`, the Python tests (`python3 tests/unit.py`), ShellCheck (`bash tests/shellcheck.sh`) and the Compose validation, plus the acceptance suite `tests/integration.py` when a task touches the Docker, desktop or GPU lifecycle.
9. **Run the acceptance suite only once, at the very end, after all requested work is done**, not after each individual task. `python3 tests/integration.py` is slow: it needs WSL, both catalog images and the manager built, and it creates real containers. During development rely on the unit tests, `build`, `clippy` and `fmt`, then run the acceptance suite a single time before finishing. New acceptance phases and assertions may still be *written* per task; just do not *execute* the suite until the end. Ordinary hosted CI has no WSL GPU; do not claim it verifies GPU, Unity or physical microphone hardware.
10. **Run the full test suite locally before finishing, CI is expensive.** GitHub Actions minutes cost real money; never lean on CI to catch a failure we could have caught locally. Before finishing any task, run the **complete** suites, not a filtered subset (`cargo test files::` passing tells you nothing about the rest of the crate): `cargo test --locked`, `bun run test` and `python3 tests/unit.py`. For timing-sensitive or flaky tests, run the affected test several times (a loop) to confirm stability, not just once. This is in addition to the single end-of-work acceptance run (rule 9).
11. **UI-only changes skip the acceptance run.** When every change in a task is confined to the frontend sources (`core/web/`: `.ts`/`.tsx`/`.html`/CSS/SVG and `core/web/public/`) with **no** Rust, Python helper, Docker, Compose, WSL package, dependency or configuration change, do **not** run `tests/integration.py`; it exercises the Docker and desktop path a UI-only change cannot affect, so it adds no coverage. Verify with the frontend's own checks instead: `bun run lint`, `bun run test`, `bun run build`, and inspect the live desktop, both themes and a narrow viewport. Save screenshots using the actual page width, then open the saved file to verify it. Restore temporary viewport overrides. Rules 9 and 10 still apply the moment a task touches anything outside `core/web/`.
12. **Never run a benchmark or a load test without asking first.** This machine runs other work; a number measured while something else is compiling or serving is not a number, and the load itself takes the machine away from its owner. That includes `wrk`, `ab`, `criterion`/`cargo bench`, any loop that hammers the manager or a desktop container, and any long release or image build started only to time it. Ask, name what you want to run and roughly how long it takes, and wait for a yes. When the answer is no, or when nobody is there to ask, reason from the code and say plainly that the claim is unmeasured rather than measuring it anyway. Correctness checks that happen to take a while (`cargo test`, `tests/integration.py`, one image build to verify it builds) are not benchmarks and need no permission.
13. **Run the gates exactly as CI runs them, on the toolchain CI uses.** Rule 8 says to prefer the project's own checks; this says to spell them the way the `checks` job in `publish.yml` spells them, because a weaker spelling is a check that passes locally and fails on push. The ones that matter are `cargo fmt --check`, **`cargo clippy --locked --all-targets -- -D warnings`** and `cargo test --locked`, and both Compose manifests validated with `.env.example`, including the `images` and `https` profiles. Two differences are easy to miss: `--all-targets` compiles tests and examples a plain `cargo clippy` never sees, and `-D warnings` turns a warning into a failure, so *counting* warnings and finding none is not the same check.
    - **The toolchain is pinned, so it moves only with a commit.** `rust-toolchain.toml` names the Rust release the `checks` job installs (`rustup toolchain install` without a name reads it) and every `cargo` run through rustup in the repository uses, so a clippy release cannot turn a commit that changed only a markdown file red. `core/manager/Dockerfile` builds on the `rust` image of the same release, and `tests/test_pinned_versions.py` holds the two equal and the `bun-version` of the workflow equal to the manager image's `oven/bun`. Raising the release edits both files together, as Dependabot's monthly infrastructure pull request does, and that pull request also fixes whatever the new clippy finds. Before concluding anything about a clippy failure, check that `cargo clippy --version` in the repository names the release of `rust-toolchain.toml`: a cargo outside rustup, or `RUSTUP_TOOLCHAIN` set, ignores the file, and you would be debugging a lint your compiler does not have.
    - **A lint that is wrong for the code is allowed where it fires, with the reason written next to it**, not switched off across the crate. A crate-wide `allow` also disarms it for the code that has not been written yet.
14. **A check that guards two languages belongs on the side whose change breaks it.** Several things here cross the Rust/JavaScript/Python boundary: the MCP tool list in `core/manager/src/mcp/tools.rs` against what `core/bridge/mcp_bridge.py` relays and `docs/MCP.md` documents, the API routes in `core/manager/src/api.rs` and `core/manager/src/api/` against `core/web/src/` and `docs/API.md`, the image catalog `images/desktop/profiles.json` against the Rust default image reference, the Compose manifests and `.env.example`. Each of those is broken by an edit on one particular side, and it must be asserted from *that* side, because that is the side whose suite the edit actually runs: rule 11 lets a UI-only change skip the acceptance suite, and a Rust change gets `cargo test` and `clippy` and never `bun run test`. A check that lives on the far side is a check nobody runs.
    - **Both sides is fine and usually right**, because they catch different mistakes: from Rust, "something was added here with no entry there"; from JavaScript or Python, "there is an entry for something no longer served". Neither is redundant. Having only the far one is.
    - **A generated file checked into the repo is the same trap.** If a script has to be re-run by hand after a change, assume it will not be; assert the file is current from the side that invalidates it.
15. Add tests for meaningful behavior or regressions, not for cosmetic changes or assertions that only repeat the implementation.

## Code structure

16. **Rust unit tests live in a sibling `<file>_tests.rs`, never inline.** A module's tests go in a file next to it, wired in with the three lines at the bottom of the module:
    ```rust
    #[cfg(test)]
    #[path = "files_tests.rs"]
    mod tests;
    ```
    The test file opens with a `//!` doc comment saying what about this module the tests are pinning down, and starts with `use super::*;`, everything private to the module is still reachable, so nothing has to be made `pub` for a test. This is not cosmetic: a module and its tests grow at different rates, and an inline `mod tests` puts a thousand lines of test between the reader and the end of the file it belongs to. It also keeps `<file>.rs` honest about its own length. A fixture the tests of unrelated modules share goes into `core/manager/src/test_support.rs`, while one only a module's own submodules share stays in that module's test file, as in `backup_tests.rs`; a new inline `mod tests { ... }` block is not acceptable. `#[cfg(test)]` helpers that the production code itself uses (a constructor, a fixture) stay in place, only the `mod tests` block moves.
17. **Rust files should stay under a thousand lines, test files excepted.** This is a guideline against code smell, not a hard limit: nothing fails because a file is 1050 lines. What it is really asking is that responsibilities be spread out, that a big single file be preferred as several small ones, and that the structure nest, a module beside its `mod/` directory beside that directory's own modules, so somebody opening the project can find where a thing is without reading. Follow Rust idiom while doing it: a `foo.rs` next to a `foo/`, `pub(crate) use` facades so a split is a pure move with no call-site churn, and names that say what the module is for rather than what it was cut out of.
    - **A file over the line is worth *asking* the question of, not automatically splitting.** The criterion was never the number, it is how many distinct subjects the file holds. A file that is one subject stays whole at 1200 lines; a file that is four subjects should have been four files at 600.
    - **Skip a file that is close to the line, or where splitting would damage the structure.** Moving twenty lines to buy a number is churn.
    - **When the objection is "too much state crosses any cut", count it before believing it.** The count is how many values bound outside a candidate cut are read inside it. Strip comments and strings, and exclude struct-literal keys, field accesses and shadowed inner bindings. A high count often points to a missing type rather than an unsplittable function.
    - **Verify a split is a pure move by diffing the test-NAME set, not the count.** `cargo test -- --list`, sorted, before and after. A hand-picked line boundary silently ate a `#[test]` attribute four times in one sweep and the suite stayed green each time, because the count of remaining tests is not what you are checking.

## Configuration surfaces

25. **A setting is an environment variable read once at startup, and `.env.example` is its only catalog.** The manager is configured through `core/manager/src/config.rs` from the environment that Compose passes it; there is no settings database, and `.env` is the only place a value is kept. The dashboard's **Management** page shows them through `Config::shown`, with `ADMIN_PASSWORD` and `MCP_TOKEN` as set or not set and never their values; a setting added there needs a section in `core/web/src/lib/settings.ts` and a `settings.about.<NAME>` line in every catalog, which `core/manager/src/config_tests.rs` asserts. In the WSL package the page also changes the settings of `EDITABLE` in `core/manager/src/config.rs`: the manager checks a change with the same `Config::parse` it starts with (`core/manager/src/config/changes.rs`), and `thoric apply-settings`, run as root by `thoric-settings.service`, writes it into `.env` and recreates the manager. Sign-in, the root MCP and its token and what only Compose reads stay CLI only (`thoric settings`). A new variable that is read anywhere else than `core/manager/src/config.rs` is a second surface that can drift from the first, and a bug, not a shortcut.
26. **Adding a setting means touching all of its surfaces in the same commit:** the field in `core/manager/src/config.rs` with its default, the documented line in `.env.example`, the `environment:` entries in both `compose.yml` and `compose.ghcr.yml`, the explanation in `docs/INSTALLATION.md`, and the copy of `.env.example` and `compose.ghcr.yml` that the WSL package and the manager image bundle (they copy the files, so nothing to edit there, but rebuild and re-verify them). Decide whether the Management page may change it: an editable setting goes into `EDITABLE` in `core/manager/src/config.rs` and `DASHBOARD_SETTINGS` in `packaging/wsl/thoric`, which tests on both sides hold equal, gets a control in `FIELDS` in `core/web/src/lib/settings.ts` unless a text field suits it, and is named in `docs/INSTALLATION.md` and `docs/API.md`; one that is not stays out of all of them. A setting that reaches only one surface is incomplete work.
27. **A variable that is removed or renamed gets a hint, in the same commit.** An installation keeps its `.env` across upgrades and nobody re-reads `.env.example`. Startup must refuse, or at least log clearly, when a removed or renamed variable is still set, naming its replacement and the release that removed it, so an upgrade does not silently fall back to a default. A variable whose name is reused with a new meaning is the one case a refusal cannot catch, so a rename never reuses an old variable's name. A changed default needs no hint, but it is a release-note entry, since the people it affects are precisely the ones who never wrote the variable.

## Language

28. Use **English** in all changes (code, comments, commit messages, docs, UI copy). The interface's translations in `core/web/src/locales/` are the one exception, and they follow the English catalog.
29. **Never use the em dash (`—`, `–`).** Write a comma instead, or split the sentence. This applies everywhere: code comments, documentation, commit messages, UI strings and job log messages. A parenthetical that a comma cannot carry is usually two sentences.

## Feature planning

30. **GitHub Issues is the active feature backlog.** Record new feature ideas there; do not create a planning markdown file in the repository. `docs/BUG_HUNT.md` is a historical verification record, not a to-do list.

## Releases

31. **A version bump edits every version in the same commit:** `core/manager/Cargo.toml`, `Cargo.lock` and `core/web/package.json` (`bun.lock` records no version of its own). The tag is `vX.Y.Z` on that commit; tagging and pushing the tag happen only at the maintainer's explicit request (rules 1 and 7).
32. **A release runs these first, and they are not optional.** Each is cheap compared with a published image that has to be pulled back:
    1. **The ordinary gates** from rules 8, 10 and 13, as CI spells them, and one `python3 tests/integration.py` inside WSL with both catalog images and the manager freshly built.
    2. **`cargo audit` and `bun audit`.** An advisory published the day before a release is still an advisory in the release. The `audit` job runs them for pull requests only, as they were when the pull request last changed, so a release runs them again on the day: `cargo audit` from the repository root and `bun run audit` from `core/web` (`docs/DEVELOPMENT.md`).
    3. **Fresh screenshots under `docs/screenshots/`** captured from a live instance at the documented widths, opened and checked after saving. They go stale silently, which is the whole problem: an old screenshot looks exactly like a current one.
    4. **The WSL package**: build `dist/thoric.wsl` with `packaging/wsl/build.sh`, install it under a test name, run the first-start setup, confirm Docker and the NVIDIA runtime inside it, then unregister the test distribution. The release workflow attaches this package, and it is built nowhere else.
    5. **Compose validation of both manifests with `.env.example`**, since the published `compose.ghcr.yml` is what an installation actually runs.
    6. **A manual run of the Publish containers workflow is a real publish**, there is no rehearsal mode; so the gates above are the rehearsal. Tag only after they are green; a tag is the one run that cannot be retried under the same name.

    **Report each one's result, including the boring ones.** A release note that says "tests pass" and nothing about screenshots or the WSL package is indistinguishable from one where they were never checked.
33. **Cutting a release includes a config audit over the whole cycle.** Run `git diff <latest tag>..HEAD` over `core/manager/src/config.rs`, `.env.example`, both Compose manifests and every `std::env::var` read. Rule 27 records changes one at a time, which is exactly the kind of thing that gets forgotten in the moment; a release is the last point where fixing it still costs nothing. For every variable removed, renamed or reshaped in the range, check that startup has a hint for it and the release notes name it. **Report the result explicitly, including when it is empty.** Say what range was audited and what was found ("14 commits, 3 touched the config surface, every removed variable has a hint"). A silent pass is indistinguishable from a skipped check.
